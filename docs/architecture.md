# Архитектура первой недели

Объём согласован по разделу 6 документа «Проектная документация: Неделя 1 —
Foundation и архитектура»: сущности из API-контрактов раздела 4, Alembic-миграция
и CategorizationService со справочником раздела 3. Остальная спецификация
описывает целевой MVP, а не готовую функциональность этой ветки.

Как в эталонном accessa, HTTP-слой отделён от сервисов и репозиториев, зависимости
передаются через FastAPI Depends и конструкторы. SQLAlchemy 2 используется
напрямую, без дополнительной ORM-обёртки или универсального BaseRepository.
Статические справочники читаются через репозиторий, отдельный сервис для
простого чтения категорий не нужен.

## Данные

| Таблица | Назначение и инварианты |
| --- | --- |
| users | UUID, уникальный нормализованный email, хэш пароля, имя, дата создания |
| categories | Стабильные ID 1–11, название, группа NEEDS/WANTS/SAVINGS/INCOME/OTHER |
| category_rules | MCC или regex, категория и приоритет, уникальная пара тип/паттерн |
| user_rules | Правило конкретного пользователя и нормализованного мерчанта |
| transactions | Сумма, направление, дата, категория, мерчант, комментарий, MCC, confidence и requires_review |
| goals | Пользователь, название, целевая сумма, срок |
| goal_contributions | История виртуальных пополнений; прогресс вычисляется как сумма пополнений |
| discounts | Партнёр, категория, заголовок, процент, промокод, URL и срок действия |

Деньги — Decimal/Numeric(14, 2), положительная сумма; направление задаётся DEBIT
или CREDIT. Все суммы MVP в рублях. Timestamp с timezone сохраняет момент
времени; границы календарных периодов должна задавать будущая аналитика.
Health Score и persona не хранятся как константы профиля: они вычисляются из
транзакций и целей в следующем этапе. Геймификация и статьи SHOULD HAVE
не входят в схему этой недели.

Удаление пользователя каскадно удаляет его правила, операции, цели и пополнения.
Категорию, на которую ссылаются операции, правила или офферы, удалить нельзя.
Индексы поддерживают выборку операций по пользователю/периоду, целей по
пользователю, пополнений по цели и предложений по категории/сроку.

Дедупликация импорта обеспечивается уникальной парой `(user_id, import_hash)`.
Будущий парсер формирует SHA-256 из нормализованных суммы, направления, даты
и описания. Для ручного ввода import_hash = NULL, поэтому одинаковые ручные
операции допустимы. Сам парсер и вычисление хэша пока не реализованы.

## Категоризация

Сервис принимает явные user_id, merchant_name, raw_description, mcc_code
и operation_type. Репозиторий получает сессию извне; сервис не открывает
соединений и не фиксирует транзакций.

1. Личное правило: поиск по user_id и `merchant_name.strip().lower()`, confidence 1.00.
2. MCC для расходной операции: точное совпадение четырёх ASCII-цифр, confidence 0.95.
3. Regex по мерчанту и описанию без учёта регистра, confidence 0.80.
4. Категория 11 «Другое / Не определено», confidence 0.00, requires_review = true.

Приходы не классифицируются как расходы по MCC мерчанта: для CREDIT используются
ключевые слова доходов; неизвестный приход также требует проверки. Личное
правило остаётся первым независимо от направления операции.

Seed содержит все 10 категорий и MCC/ключевые слова из документа, плюс fallback.
Более конкретные keyword-правила красоты идут перед супермаркетами: «Магнит
Косметик» не должен попадать в продукты только из-за слова «магнит».
Для коротких паттернов «t2», «ерц» и «вита» заданы границы слова; точка в «дом.ру»
экранирована. Остальные паттерны сохранены по спецификации.

Confidence — назначенный вес источника правила, а не измеренная точность.
Порог 80% на реальных банковских выписках и SLA импорта проверяются после
реализации парсера на предоставленной банковской выборке.

## Миграции и конфигурация

Начальная миграция содержит фиксированную схему и seed; она не импортирует
актуальные модели или данные сервиса. Изменения справочника в следующих
неделях оформляются новой миграцией. Alembic использует asyncpg через
AsyncConnection.run_sync, согласно официальному asyncio recipe.

FINSMART_DATABASE_URL обязателен для БД и миграций. Liveness и OpenAPI доступны
без подключения к БД. CORS по умолчанию закрыт; список разрешённых origins
задаётся FINSMART_CORS_ORIGINS в виде JSON-массива. Конфигурация и engine
кешируются в пределах процесса, сессия создаётся на запрос и закрывается после
него; engine освобождается при завершении приложения.
