# Неделя 2: импорт, категоризация и бюджет

Запуск и все проверки — через Docker из [инструкции](../README.md).
HTTP-слой находится в `src/routes`, бизнес-логика — в `src/modules`,
SQL-запросы — в репозиториях модулей. Роуты не обращаются к БД напрямую.

## Авторизация

В Swagger сначала выполните `POST /api/v1/auth/register`:

```json
{"email":"user@example.com","password":"My-password-123!","full_name":"Иван Иванов"}
```

Пароль: 10–128 символов; email нормализуется в нижний регистр.
Ответ содержит `user_id`, `email`, `access_token`, `refresh_token`, `token_type`.
Вставьте `access_token` в **Authorize**. Во всех защищённых запросах используется
`Authorization: Bearer <access_token>`; пользователь берётся из токена.

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/v1/auth/register` | Регистрация, 201; занятый email — 409 |
| `POST /api/v1/auth/login` | Вход: email и password; неверные данные — 401 |
| `POST /api/v1/auth/refresh` | Новая пара по JSON `{"refresh_token":"…"}` |
| `GET /api/v1/users/me` | Профиль текущего пользователя |

Пароли хранятся как Argon2id-хеши. JWT проверяет подпись HS256, срок,
issuer, audience, идентификаторы и тип токена. Access живёт 60 минут,
refresh — 30 дней. Refresh-сессия хранит только SHA-256 токена; обновление
атомарно заменяет её, повторное использование старого refresh возвращает 401.
Ошибки валидации не возвращают введённые пароли или токены.

Настройки: `FINSMART_JWT_SECRET` (не менее 32 символов),
`FINSMART_ACCESS_TOKEN_MINUTES`, `FINSMART_REFRESH_TOKEN_DAYS`.
Без постоянного ключа токены перестают действовать после перезапуска процесса.
Для сохранения входа задайте ключ через окружение Compose; не коммитьте его.
Текущий Compose запускает один процесс API. Для нескольких нужен общий ключ.

## Импорт

`POST /api/v1/transactions/import-statement` — multipart:

- `file`: CSV или XLSX, не более 5 МиБ и 1000 строк операций;
- `bank_hint`: `auto` (по умолчанию), `tbank`/`tinkoff`, `sber`, `vtb`.

В Swagger выбирайте файл через форму запроса. Выписки принадлежат текущему
пользователю; передавать чужой `user_id` не требуется и нельзя.

| Банк | Обязательные заголовки |
| --- | --- |
| Т-Банк | Дата операции; Сумма операции; Валюта операции; Описание; Статус |
| Сбер | Дата операции; Время операции; Описание операции; Сумма в валюте счета; Валюта счета; Статус |
| ВТБ | Дата и время операции; Сумма операции; Валюта операции; Тип операции; Статус операции; Детали операции (либо Описание, либо Детали операции / Описание) |

`MCC`, `Категория` — необязательные колонки. Регистр заголовков и ё/е
не влияют на распознавание. CSV: UTF-8/BOM либо Windows-1251, разделитель
`;` или `,` с корректным CSV-экранированием. XLSX: активный лист, первая строка
содержит заголовки; формулы запрещены. Лимит распакованного XLSX — 30 МиБ,
200 ZIP-записей и 32 колонки. XML читается с defusedxml.

Дата: `ДД.ММ.ГГГГ ЧЧ:ММ[:СС]` или ISO 8601. Дата Excel в отдельной колонке
Сбера поддерживается. Даты без timezone относятся к
`FINSMART_FINANCIAL_TIMEZONE` (по умолчанию `Europe/Moscow`), сохраняются в UTC.

Выполненные статусы: `OK`, `Исполнена`, `Исполнено`, `Успешно`.
Нулевые суммы и известные неисполненные статусы (`FAILED`, `В обработке`,
`Отклонена`, `Отменена`, `Отклонено`, `Не исполнена`) пропускаются.
Неизвестные статусы, валюты и неоднозначные направления отклоняют файл целиком.
Валюты RUB/RUR/руб/₽ приводятся к RUB. Сумма положительная, максимум
12 цифр до запятой и два после; знак определяет направление, а не размер.

У Т-Банка отрицательная сумма — расход, положительная — приход.
У ВТБ направление задаёт `Тип операции`: списание/расход/оплата/debit или
пополнение/зачисление/доход/credit. Сбер допускает эту же колонку; иначе
отрицательный знак означает расход, `+` — приход, либо используются явные
маркеры описания: списание/оплата/покупка и зачисление/пополнение/зарплата.
Положительная сумма Сбера без этих признаков считается неоднозначной.

`StandardTransactionDTO` содержит `external_id`, `bank_source`,
`transaction_date`, `amount`, `operation_type`, `currency`, `raw_description`,
`merchant_name_clean`, `mcc_code`, `bank_category_raw`.
Описание сохраняется целиком, мерчант очищается от технических префиксов,
терминальных суффиксов, повторных пробелов и приводится к нижнему регистру.
MCC — четыре цифры; внутри DTO это число, для поиска правил дополняется нулём слева.

Идентификатор — SHA-256 UTF-8 JSON-массива
`[user_id, bank_source, UTC-date, amount-with-2-decimals, direction, cleaned-merchant]`.
Порядок фиксирован, разделители `,` и `:`, без ASCII-экранирования.
Одинаковые операции по этим полям считаются дублями, включая две покупки
в одну секунду с одинаковой суммой и мерчантом. Это ограничение заданной
формулы; банковский уникальный ID в ней не предусмотрен.
Уникальность `(user_id, import_hash)` и `ON CONFLICT DO NOTHING` защищают
повторный/параллельный импорт. Ошибка любой строки не сохраняет часть файла.

Ответ:

| Поле | Значение |
| --- | --- |
| `total_rows` | Все непустые строки операций |
| `skipped_rows` | Нулевые/неисполненные операции |
| `total_parsed` | Валидные выполненные операции, включая дубли |
| `imported_count` | Новые сохранённые операции |
| `duplicates_skipped` | Дубли внутри файла или уже в БД |
| `successfully_categorized` | Валидные операции без fallback |
| `recognition_rate` | Их доля среди `total_parsed`, 0–1 |
| `accuracy_rate` | Совместимый псевдоним recognition_rate, **не измеренная точность** |
| `imported_transactions` | Только новые операции с категорией, confidence, requires_review |

В операциях ответа также есть совместимые `date` и `merchant_name` наряду
с каноническими полями. Денежные значения в JSON — числа; внутри используется Decimal.

## Категоризация и исправления

Порядок строго фиксирован:

1. Правило пользователя по очищенному мерчанту — confidence 1.00.
2. MCC для расхода — 0.95.
3. Regex системного справочника с учётом направления — 0.80.
4. Явный маппинг банковской категории — 0.75.
5. «Прочее», requires_review=true — 0.00.

Confidence — вес источника, не статистическая точность. Справочник содержит
11 категорий и 47 правил; добавлены латинские варианты мерчантов к правилам
первой недели. Для файла правила загружаются пакетно, запросов на каждую строку нет.

`GET /api/v1/transactions?limit=100&offset=0` возвращает только свои операции
от новых к старым; limit 1–1000.

`PATCH /api/v1/transactions/{id}/category`:

```json
{"category_id":2,"save_as_global_rule":true}
```

Без сохранения правила меняется только выбранная операция. С флагом `true`
меняются также существующие операции этого пользователя с тем же мерчантом,
создаётся/обновляется его личное правило для будущих импортов. Флаг означает
глобальность внутри пользователя, а не общее правило для всех пользователей.
Чужая или отсутствующая операция — 404, неизвестная категория — 422.

## Аналитика 50/30/20

`GET /api/v1/analytics/budget?from_date=2026-10-01&to_date=2026-10-31`.
Обе границы включаются как календарные даты финансовой timezone.
Без границ используется текущий календарный месяц; одна граница — 422.
Максимум 367 календарных дней. Агрегация выполняется одним SQL-запросом
с обязательным фильтром владельца.

- `summary`: доход, расход, чистый баланс.
- `budget_50_30_20`: needs/wants/savings; сумма, доля в процентах,
  целевая доля/сумма, отклонение `actual - target`.
- `by_categories`: расходы и их доли среди всех расходов.
- `income_base`: доход; если дохода нет — сумма расходов и `deficit_financing=true`.
- `unallocated_expense`: расходы «Прочее» и расходы в категории доходов.
- `budget_score`: показатель дисциплины Wants, 0–100.

Кредиты категории Savings (переводы между своими счетами) не являются доходом.
Все дебеты входят в общий расход. Savings = явные дебеты Savings +
`max(доход − все расходы, 0)`; остаток не учитывается дважды.
План: 50%, 30%, 20% от income_base. Неопределённые расходы не приписываются
произвольно Needs или Wants, поэтому суммы трёх групп могут не покрывать всю базу.

В исходном документе формула budget_score отсутствует; явно принято:
100 при Wants ≤30% базы, линейное снижение до 0 при Wants ≥50%.
Без базы score=0. Это бюджетный показатель, не полный Financial Health Score
следующих недель. Для фронтенда предоставлен отдельный `/analytics/budget`;
полный `/analytics/dashboard` с ещё не реализованными метриками не подменяется.

## Проверки и реальный эталонный набор

Unit/API/PostgreSQL-тесты покрывают форматы и кодировки, нормализацию,
повреждённые файлы, атомарность, дубли, изоляцию пользователей, исправления,
JWT/refresh, миграции, бюджет и импорт 1000 строк менее чем за 3 секунды.
Есть 300 **синтетических** размеченных регрессионных операций, по 100 на банк.
Это проверка известных сценариев, а не доказательство точности на реальных данных.

Порог ≥80% на реальных данных пока **не подтверждён**: заказчик предоставит
обезличенный набор позже. Требуется минимум по 100 выполненных ненулевых
расходов каждого банка, минимум 8 категорий суммарно, без дублей.
Добавьте в каждый CSV/XLSX колонку `expected_category_id` с экспертной разметкой;
остальные колонки соответствуют таблице форматов выше.

После запуска Compose положите три файла в отдельную локальную папку `golden`
и выполните из корня репозитория:

```bash
docker compose run --build --rm -v "$PWD/golden:/golden:ro" test \
  python -m scripts.evaluate_categorization \
  --tbank /golden/tbank.csv --sber /golden/sber.xlsx --vtb /golden/vtb.xlsx
```

Скрипт создаёт отдельного пользователя, импортирует файлы через реальный API,
сравнивает категории по external_id и печатает JSON с точностью каждого банка
и общей точностью. Код завершения 1, если любая точность ниже 80%; иначе 0.
Учётная запись и операции проверки остаются в локальной БД. Используйте
обезличенные данные и отдельную локальную среду. Не добавляйте выписки в Git.

Проверка живого API без эталонного набора:

```bash
docker compose run --rm test python -m scripts.smoke_week2
```

Она проверяет регистрацию, импорт, повторный импорт, бюджет и ротацию refresh.
CI выполняет её после сборки и запуска Compose.

## Миграции

`0002_statements` добавляет исходное описание, банк, валюту и банковскую
категорию операций, ограничения и девять regex-правил. Старые операции
получают MANUAL/RUB/пустое исходное описание, сохраняя прежние значения.
`0003_auth` добавляет refresh-сессии. Миграции обратимы; согласованность
с моделями и upgrade/downgrade проверяется на PostgreSQL.
